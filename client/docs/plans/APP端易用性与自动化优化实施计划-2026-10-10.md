## 1. 目标与范围

优先让用户能够开通自动记账、看清运行状态、稳定选择自动入账目标，并在漏记或积压时找到原因和处理入口。复用四路识别、候选确认、判重、分类学习和重试能力，不重复建设已有功能。

| 优先级 | 目标 | 完成后的用户行为 |
|---|---|---|
| P0 | 开通容易 | 从一个入口完成服务检查、账本与账户选择、来源授权和实际验证 |
| P0 | 状态可信 | 首页能区分等待识别、需要确认、已入账待同步和需要修复 |
| P0 | 入账稳定 | 切换浏览账本不改变后台入账目标；重试不重新选账本 |
| P0 | 积压可追踪 | 未处理事件可恢复；容量不足、过期和丢失风险有明确提示 |
| P1 | 确认省操作 | 只补有问题的字段，普通忽略可撤销，重复处理有清楚对比 |
| P1 | 纠错可复用 | 用户决定是否记住分类或账户规则，并可管理规则 |
| P1 | 少打扰、好补记 | 通知偏好可选；识别记录可直达快捷补记 |

范围边界：

1. 保留时间裁决的两档现状：“未识别到交易时间或时间由模型推测”仍由自动入口直接过滤（time_missing / time_inferred），不改成默认时间、不自动转入待确认；“时间精度不足（如仅有日期）”等弱精度情形照旧进入待确认（time_precision_weak），本计划不改动该档。手动补记必须由用户主动发起并确认时间。
2. 保留来源白名单、交易语义校验、幂等、判重和用户确认边界。不恢复已主动移除的大额/异常支出提醒，不单纯降低模型置信度阈值。
3. AI 调用继续通过既有服务端中转，密钥只在服务端保存；不新增客户端直连 LLM 或明文密钥下发。
4. 本计划不新增服务端接口，不调整移动端与服务端同步协议，不实施 Web 端改造。若实施中必须跨入服务端，另行列清范围，并先读取服务端开发与同步契约。
5. Android 系统权限仍由用户操作；不得把跳转设置页或用户勾选“已完成”当成权限及监听服务正常的证明。
6. 发布、生产数据修复及任何 Git 提交不在本次保存文档的授权范围内。

## 3. 用户流程与状态口径

### 3.1 统一开通入口

“我的 → 自动记账”作为主入口，首页状态卡提供快捷进入。智能记账页保留拍照、语音、AI 能力设置，并链接至同一个自动记账配置页；原“自动化”中的周期记账和提醒改用清楚的分组名称，保留原功能。

开通流程：连接服务与检查 AI → 选择自动入账账本/账户 → 选择来源并授权 → 检查后台运行设置 → 完成一次实际来源验证。

逐步保存进度，允许暂时跳过非必要来源。先展示支付通知和银行短信；详情页识别、截图按需开启。各来源具体可用性以当前设备与构建渠道为准，保留已有渠道裁剪。权限解释在用户开启对应来源时显示，不一次性索取全部权限。

普通设置展示“符合条件自动入账 / 每笔确认后入账”。说明未结算、无可信时间等结果仍被过滤，疑似重复等结果仍需确认。演练模式、模拟注入、判重豁免放在高级设置，演练开启时首页明确显示“仅识别，不生成账单或候选”。

### 3.2 首页状态卡

单张紧凑卡片呈现可行动状态，示例：“通知权限正常 · AI 暂不可用；已保存 3 条，恢复后继续处理”。

| 状态维度 | 判定依据 | 操作 |
|---|---|---|
| 用户开关 | 当前来源配置 | 去开启或暂停 |
| 系统权限 | 实际权限查询结果 | 跳转对应授权页 |
| 监听连接 | 原生连接/解绑状态与观察器注册状态 | 检查系统设置；无法查询则显示“待验证” |
| AI 能力 | 既有 AI 运行时状态、能力绑定与最近实际调用结果 | 登录、检查配置或等待恢复 |
| 处理队列 | 原生积压、事件处理/重试状态和待确认子项 | 查看识别记录或待确认 |
| 云同步 | 既有同步状态 | 查看同步状态，不重复识别已入账交易 |

“已配置”“监听已连接”“实际事件识别成功”分开显示。记录最近捕获与处理时间，不能仅凭长期无新事件判定断开。状态查询失败不显示“正常”；未选择的来源不算故障。

首页、配置页、开通页共用一份状态源。优先事件驱动更新，在页面恢复前台时补查；避免每次页面重建或高频轮询都调用原生桥及网络。

### 3.3 漏记解释与补记

建立统一“结果＋原因＋动作”映射：time_missing 显示“没有识别到交易时间，未入账”；time_precision_weak 显示“只识别到日期，需确认时间”；登录失效显示“需要重新登录，事件暂存”；AI 不可用显示“等待恢复后处理”；重复候选显示“与已有记录可能相同”。内部错误放在可展开诊断区域，普通列表不展示堆栈或凭据。

手动补记带入可用的可信字段，时间缺失必须让用户填写并确认；不带入模型猜测时间。原文/图片已清理时明确说明，只使用仍可用的结构化摘要；不承诺所有过滤事件都能恢复原始材料。

### B3（P0）：原生积压保护与恢复交接

任务：

1. 将四路待处理队列统一到应用私有目录的原生持久化存储，建议使用 Android 自带 SQLite 事务能力，避免引入额外同步服务或依赖 Flutter/AI 就绪才能接收事件。不直接从 Kotlin 打开 Drift 数据库，不并行创建第二套识别器。
2. 统一封套包含事件键、来源、捕获时间、发生时间、用户/目标快照、必要重放材料、迁移版本。保持原有来源标识与指纹兼容，不把同金额同商家当作同一事件。
3. 分批读取，有界处理。原生队列在 Dart 处理达到可 ACK 结果后移除；若提前交接，必须先确认事件元数据及完整可重放材料已持久化。不得仅因 event store 已创建元数据行而 ACK。冷启动期桥接通知可能静默失败（现状已有此竞态记录），入队与桥接通知解耦、靠 peek-drain 补齐，不得依赖单次桥接投递成功。
4. 区分“已交给 Dart”与“已完成”。先保留当前终态 ACK 方式；只有跨存储交接、崩溃重放和重复 ACK 测试通过，才启用提前交接。交接不写交易成功指纹，不跳过语义闸门。
5. 设置容量、字节数和有效期；接近容量先提示并触发有界处理，不能再无提示移除最旧事件。容量完全耗尽时拒绝新入队并记录可见的最小损失摘要；不能宣称任何资源条件下零丢失。
6. 首版候选参数：每来源 500 项、总体材料 20 MiB、未完成处理材料最长 72 小时；这些是待 B0 验证的工程起点，不是已有配置或最终产品承诺。截图只保留可访问路径/URI，不私自复制原图；材料失效时说明不能重放。
7. 临时重放材料与可选“历史原文留存”用途分离。默认只保留处理所需时间，终态后清除；超时清理前记录无原文的过期摘要。尊重用户主动清理，不因关闭历史原文留存而开启服务器上传；隐私说明须说明处理队列的临时存储。
8. 迁移采用旧队列快照 → 新库按事件键去重写入 → 校验 → 迁移标记 → 切读新库。迁移时捕获继续可靠写入；导入可重复执行，失败继续读旧队列，不先清空旧值。
9. 复用已有联网/登录恢复和周期重试；处理期间暂停、注销、切账号都必须隔离事件，不将上一账号材料送给下一账号。

## 5. 数据兼容、并发与回退

1. 新配置使用带版本的独立键，旧设置只读导入，不删除旧值；默认不自动开启过去关闭的识别来源，不修改 AI 隐私同意记录。

3. 原生队列使用独立库与版本，和 Drift 分工明确。跨库操作无原子事务，使用“先写目标、确认可重放、再 ACK”及事件键幂等处理崩溃窗口。
4. 历史交易不因本计划批量改账本、改账户或重分类；修复历史数据另列清单取得授权。待处理事件目标无效时暂停，不自动迁移至其他账本。

6. 配置保存、原生目标缓存更新和捕获需有版本检查。旧目标继续存在于已捕获事件；配置同步失败时显示待生效，不让 UI 宣称新目标已应用。
7. 原生队列切换前保留旧格式备份。过渡期新旧读写路径使用同一事件键去重；安全回退版必须能够读取新队列或执行停止捕获后的受控导出。不得直接降级到不会读取新队列的旧 APK。
8. Drift 增量字段迁移尽量保持旧读兼容；不通过降库版本或删除表回退。发布前验证数据库可读性，失败用备份恢复到验证过的版本，不在真实用户库试错。
